# Peripherals

Here you can find the documentation for the peripherals of X-ALP. All of them are register-interface slaves in the peripheral domain (`0x2000_0000` by default); their final addresses are listed in the [Address Map](../Configuration/AddressMap.md), and in software they are available through the `<NAME>_BASE_ADDRESS` macros of `core_v_mcu.h`. To add or move peripherals, see [Peripheral Configuration](../Configuration/PeripheralConfiguration.md).

When you run `make mcu-gen`, the register documentation of each peripheral is generated in `sw/device/lib/drivers/<name>/<name>_regs.md` (see [Generate peripheral registers](../How_to/GenerateRegisters.md)).

## SoC controller (`soc_ctrl`)

The SoC controller (`hw/ip/soc_ctrl`) holds the registers used to boot and to end a program:

| Register | Description |
|----------|-------------|
| `EXIT_VALID` | Set to `1` when the program ends. Drives the `exit_valid` output of the chip |
| `EXIT_VALUE` | Value returned by the program. Drives the `exit_value_o` output |
| `BOOT_SELECT` | Boot mode selection |
| `BOOT_EXIT_LOOP` | Set to release the boot ROM wait loop |
| `BOOT_ADDRESS` | Address the boot ROM jumps to |
| `SYSTEM_FREQUENCY_HZ` | Frequency of the system, in Hz |

The driver is in `sw/device/lib/drivers/soc_ctrl`.

## Boot ROM (`bootrom`)

The boot ROM (`hw/ip/bootrom`) is the first code executed by the CPU. It is built from `hw/ip/bootrom/bootrom.S` by `make boot-rom` (called by `make mcu-gen`). It:

1. clears the integer registers;
2. waits until `BOOT_EXIT_LOOP` of the SoC controller is set;
3. reads `BOOT_ADDRESS`. If it points to the LLC scratchpad, it waits for the LLC built-in self-test and locks every cache way as scratchpad;
4. jumps to the boot address.

When the program returns, the C runtime writes the return value to `EXIT_VALUE` and sets `EXIT_VALID`.

## UART (`uart`)

The [OpenTitan UART](https://opentitan.org/book/hw/ip/uart/index.html) (`hw/subsystems/uart_subsystem.sv`). The software runtime uses it for `printf`. Its interrupts are PLIC sources. The driver is in `sw/device/lib/drivers/uart`.

In simulation, the UART is connected to the UART DPI of the testbench, and its output is written to `uart0.log` (see [Simulate](../How_to/Simulate.md)). The baud rate and the reference clock assumed by software are set in `sw/device/target/sim/x-alp.h`.

## Interrupts (`rv_plic`, `rv_timer`)

Interrupts follow X-HEEP: `configs/soc.py` lists the PLIC sources with `Interrupts.add_interrupt(name, id)`, IDs contiguous from 0. The remaining IDs up to 63 become `EXT_INTR_<n>`, driven by the `ext_intr_i` port of the SoC. Each ID is a `#define <NAME>` in `core_v_mcu.h`.

The PLIC (`hw/subsystems/rv_plic_subsystem.sv`) drives the machine external interrupt (MEIP) of CVA6 and its `MSIP0` register the machine software interrupt. The timer (`hw/subsystems/rv_timer_subsystem.sv`) drives the machine timer interrupt (MTIP). CVA6 has no local interrupts. Traps use the vectored table of `sw/device/lib/crt/vectors.S`. The PLIC driver is in `sw/device/lib/drivers/rv_plic`.

## Power manager (`power_manager`)

The power manager (`hw/ip/power_manager`) does power gating and clock gating. Both are configured in `configs/soc.py`, with the instances they control (see [Power Configuration](../Configuration/PowerConfiguration.md)):

```python
Power_manager(
    power_domains=[PowerDomain("cpu", [cpu], modes=["clock_gate", "off"]),
                   PowerDomain("llc", [llc], modes=["clock_gate", "retentive", "off"])],
    clock_gates=[uart],
)
```

- A **clock gate** (`CG_<NAME>` register, one bit per block) stops the clock of its block.
- A **power domain** sleeps in one of its modes: `clock_gate` (clock stopped), `retentive` (plus isolation and retention), `off` (plus reset and power switch off, state lost). It sleeps when armed (`PD_<NAME>_SLEEP_EN`) and the cores of its `WFI_MASK` are in WFI. First it isolates the AXI ports of its blocks (`axi_isolate`: new transactions stall, none is lost) and waits for them to drain. It wakes on a source of its wake mask (PLIC sources, wake-up timer), on a debug request of its cores, or when software disarms it.
- An **external** domain has no block inside the chip: its control signals leave on the `ext_pwr_ctrl_o`/`ext_pwr_ack_i` ports.

Every gated block gets a `clock_gate_wrapper` and, in a power domain, a `power_switch_wrapper`. Like the memories, these are behavioral in simulation (`hw/simulation`), mapped to the FPGA in `hw/target/fpga/pm_cells_xilinx.sv`, and replaced with technology cells in an implementation. Isolation is only a control signal, for the power intent (UPF).

Software uses two SDK headers, generated by `mcu-gen` from the configuration and fully inline:

- `cpu_sdk.h`: `cpu_wfi()`, `cpu_cycles()`, `cpu_irq_*()`, and `cpu_sleep_cycles(mode, n)` / `cpu_sleep_until(mode, irq_mask)` that put the core to sleep in its power domain.
- `power_manager_sdk.h`: `pm_<block>_clock_gate(gated)` per clock-gated block; `pm_<pd>_clock_gate()`, `_retention()`, `_off()`, `_on()` (blocking) per power domain; `pm_<pd>_<mode>_with_cpu()` for the domains declared with `follows_cpu=True`, which only sleep together with the cores.

A call the configuration does not allow (block not configured, always on or not clock gated, mode not supported, a domain that holds the cores or follows them) fails to compile with a `_Static_assert` naming the reason. The wake-up timer uses PLIC priority 7, reserved to it.

A core switched off resumes through the boot ROM: the driver (`sw/device/lib/drivers/power_manager`) saves its context, `WAKEUP_STATE_<hart>` and `RESTORE_ADDR_<hart>` tell the boot ROM where to resume. `sw/applications/example_power_manager` exercises clock gating and the sleep modes of the LLC, `sw/applications/example_cpu_sdk` the sleep modes of the CPU, `sw/applications/example_interrupts` the PLIC.

## Last-level cache configuration (`axi_llc`)

The configuration registers of the [AXI LLC](https://github.com/pulp-platform/axi_llc), the memory subsystem of X-ALP (see [Memory Configuration](../Configuration/MemoryConfiguration.md)). The C header with the register offsets, `sw/device/lib/drivers/axi_llc/axi_llc_regs.h`, and the full register documentation, `sw/device/lib/drivers/axi_llc/axi_llc_regs.md`, are generated from the vendored IP. The main registers are:

| Register | Description |
|----------|-------------|
| `CFG_SPM_LOW` / `CFG_SPM_HIGH` | One bit per way: `1` uses the way as scratchpad, `0` as cache |
| `CFG_FLUSH_LOW` / `CFG_FLUSH_HIGH` | One bit per way to flush |
| `COMMIT_CFG` | Write `1` to apply the configuration written in `CFG_SPM` and `CFG_FLUSH` |
| `FLUSHED_LOW` / `FLUSHED_HIGH` | One bit per way, set when the way is flushed |
| `SET_ASSO_LOW`, `NUM_LINES_LOW`, `NUM_BLOCKS_LOW` | Instantiated cache geometry |
| `BIST_STATUS` | Status of the built-in self-test of the tag storage |

To switch ways between cache and scratchpad, write the new mask to `CFG_SPM`, write `1` to `COMMIT_CFG`, and wait until `FLUSHED` matches the mask, as the boot ROM does. While the LLC applies a new configuration, it does not serve requests.

## External peripheral (`ext_peripheral`)

A slot of the peripheral domain forwarded to the `ext_reg_req_o`/`ext_reg_rsp_i` port of the `x_alp` top level, to connect the registers of a peripheral outside X-ALP. See [eXtending hardware](../Extending/eXtendingHW.md).

## Pad control (`pad_control`)

The pad control registers, generated from the [pad configuration](../Configuration/PadConfiguration.md). It is available in {py:attr}`~xheep_gen.xalp.XAlp.AVAILABLE_PERIPHERALS` but not instantiated in the default configuration.
